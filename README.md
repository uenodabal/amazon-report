# Amazon 販売データ自動取得

SP-APIとData Kioskから販売実績を取得し、Googleスプレッドシートへ毎日自動で書き込みます。

| 取得するもの | 出力先シート |
|---|---|
| 注文明細 | `raw_orders` |
| ASIN別 売上・セッション・転換率 | `raw_sales_traffic` |
| 手数料・入金内訳 | `raw_finances` |
| 精算明細 | `raw_settlement` |
| **月別の実績**（例 `2026-08`） | 月ごとに1シート |
| **月次推移** | `月次推移` |
| 実行ログ | `_log` |

**データは蓄積されます。** 各シートは上書きではなく、新しく取得した期間だけを
差し替えて過去分を保持します。Amazon側のAPIには取得可能期間の上限
（精算レポートは90日、財務イベントは180日）がありますが、
**毎日実行し続けることで、その制限を超えた履歴が手元に残り続けます。**

初期設定の所要時間：**工程A 30分 → 工程B 40分 → 工程C 20分**（合計1時間半ほど）

## 工程A　アプリクライアントの作成（ソリューションプロバイダーポータル）

開発者プロフィールの審査は完了済みなので、ここに審査待ちはありません。

### A-1. アプリクライアントを作成する

1. ソリューションプロバイダーポータルの画面で **「新しいアプリクライアントを追加」** をクリック
2. 以下を入力する

| 項目 | 入力内容 |
|---|---|
| アプリ名 | `エクソプラス販売データ連携` （「Amazon」の語は含めない） |
| APIタイプ | **SP-API** |
| 対象 | **出品者（Seller）** |
| ロール | Brand Analytics / Inventory and Order Tracking / Finance and Accounting / Amazon Fulfillment |
| OAuthログインURI・リダイレクトURI | **空欄でよい**（プライベートアプリのため不要） |

3. 保存する

> **ロールについて**：購入者の氏名・住所にアクセスするロールは選ばないでください。本スクリプトが使う注文レポートは個人情報を含まない種別（`..._GENERAL`）です。

### A-2. クライアントIDとシークレットを控える

作成したアプリの行にある **「LWA認証情報を表示」** をクリックすると表示されます。

- `LWA_CLIENT_ID` — `amzn1.application-oa2-client.` で始まる文字列
- `LWA_CLIENT_SECRET` — `amzn1.oa2-cs.v1.` で始まる文字列

**シークレットはこの画面でしか確認できない場合があります。**必ずこの時点で控えてください。

### A-3. セルフオーソライゼーション（リフレッシュトークンの取得）

1. アプリの行の右端 **「⋮」** → **「Authorize」** を選択
2. 表示された画面で **「Authorize」** ボタンを押す
3. **リフレッシュトークン**（`Atzr|` で始まる長い文字列）が表示される

- このトークンに**有効期限はありません**。手動で失効させるまで使えます
- **この画面を閉じると二度と表示されません。**必ずコピーしてください
- 万一控え忘れた場合は、もう一度Authorizeし直せば再発行できます

> ⚠️ このトークンがあれば御社の売上・精算データを誰でも読めます。チャットやメールで送らないでください。

## 工程B　Google Cloudの準備

### B-1. プロジェクトを作成する

[Google Cloud Console](https://console.cloud.google.com/) で新規プロジェクトを作成します。名前は `amazon-report` などで構いません。

### B-2. APIを有効化する

「APIとサービス」→「ライブラリ」から、以下**2つ**を有効化します。

- **Google Sheets API**
- **Google Drive API**

（Drive APIも必要です。これが無いとスプレッドシートを開く時点で失敗します）

### B-3. サービスアカウントとキーを作成する

1. 「IAMと管理」→「サービスアカウント」→ **「サービスアカウントを作成」**
2. 名前は `amazon-report-bot` など。ロールの付与は**不要**（スキップ可）
3. 作成したサービスアカウントを開く →「キー」タブ →「鍵を追加」→「新しい鍵を作成」→ **JSON**
4. ダウンロードされたJSONファイルを、このスクリプトと同じフォルダに **`service-account.json`** という名前で保存する

**このJSONファイルの中身も認証情報です。**Gitにコミットしないでください（`.gitignore` で除外済みです）。

### B-4. スプレッドシートを作成して共有する

1. Googleスプレッドシートを新規作成する（名前は `Amazon販売データ` など）
2. URLからIDを控える

```
https://docs.google.com/spreadsheets/d/【ここがSPREADSHEET_ID】/edit
```

3. **右上の「共有」から、サービスアカウントのメールアドレスに「編集者」権限を付与する**

サービスアカウントのメールアドレスは `amazon-report-bot@プロジェクト名.iam.gserviceaccount.com` の形式で、JSONファイル内の `client_email` にも記載されています。

> **この共有設定を忘れるのが最も多いつまずきです。**忘れると権限エラーで書き込めません。

## 工程C　実行

### C-1. 必要なものを入れる

Python 3.9以上が必要です。

```bash
cd amazon-report
pip install -r requirements.txt
```

### C-2. 設定ファイルを作る

```bash
cp .env.example .env
```

`.env` をテキストエディタで開き、工程A・Bで控えた値を記入します。

### C-3. まず接続テスト（スプレッドシートには書き込まない）

```bash
source .env
python main.py --dry-run --days 7
```

取得件数と先頭数行が表示されれば、SP-APIとの接続は成功です。

### C-4. スプレッドシートへ書き込む

```bash
python main.py --days 30
```

シート `raw_orders` に注文明細が書き込まれます。

## 使い方

### 注文レポート（`main.py` → シート `raw_orders`）

```bash
python3 main.py                # 直近30日分
python3 main.py --days 7       # 直近7日分
python3 main.py --dry-run      # 取得のみ。書き込まない
```

### ASIN別 売上・セッション（`sales_traffic.py` → シート `raw_sales_traffic`）

セラーセントラルの「ビジネスレポート（子商品別の詳細ページ売上・トラフィック）」に
相当するデータを、**日付 × ASIN** の粒度で取得します。

```bash
python3 sales_traffic.py                  # 直近7日分
python3 sales_traffic.py --days 30        # 直近30日分
python3 sales_traffic.py --granularity SKU  # SKU単位で取得
python3 sales_traffic.py --dry-run        # 取得のみ
```

取得できる指標：発注数、売上金額、注文品目数、出荷数、返品数、返品率、
セッション数、ページビュー、ブラウザ/アプリ別セッション、カートボックス獲得率、
**ユニットセッション率（＝転換率）**

**この機能にはアプリに「Brand Analytics」ロールが必要です。**
不足していると FATAL エラーになります。その場合はソリューションプロバイダーポータルで
ロールを追加してください。

**所要時間にご注意ください。** Data Kioskは1回のクエリで1日分しか日別に分解できないため、
日数分のクエリを順番に実行します。1日あたり1〜3分かかるので、30日分では30〜60分ほど
必要です。初回の取り込みは時間に余裕があるときに実行してください。

**当日のデータは取得しません。** 数値が未確定のため、既定で前日までを対象にします。

### 手数料・入金内訳（`finances.py` → シート `raw_finances`）

売上から販売手数料・FBA手数料・プロモーション値引きを差し引いた
**実際に入金される金額**を、注文 × SKU 単位で取得します。
これがあると商品ごとの実利益が計算できます。

```bash
python3 finances.py                # 直近30日分
python3 finances.py --days 90      # 直近90日分（最大180日）
```

| 列 | 内容 |
|---|---|
| 商品代金 / 税 / 配送料 | 売上側の内訳 |
| プロモーション値引 | クーポン・セール等（マイナス） |
| 販売手数料 | 紹介料（マイナス） |
| FBA手数料 | 配送代行手数料・保管料など（マイナス） |
| **純額** | 上記をすべて合算した実入金額 |

保管手数料など注文に紐づかない費用も、`eventType` に理由を入れて記録します。

### 精算レポート（`settlement.py` → シート `raw_settlement`）

銀行入金額との照合用です。Amazonが精算サイクル（通常2週間）ごとに自動生成します。

```bash
python3 settlement.py              # 直近3件
python3 settlement.py --count 6    # 直近6件（約3ヶ月分）
```

**Amazonの仕様上、90日より前の精算レポートは取得できません。** `getReports` の
`createdSince` が90日までしか遡れないためで、これより前を指定すると
`InvalidInput: ... is more than 90 days old` になります。
本スクリプトは89日で自動的に打ち切るため、このエラーは発生しません。
それより古い精算明細が必要な場合は、セラーセントラルから手動でダウンロードしてください。

**このレポートは `createReport` でリクエストできません。** Amazonが生成済みのものを
`getReports` で探して取得する仕様です。ここを取り違えると
「Request for report type ... is not allowed at this time」で必ず失敗します。
本スクリプトは正しい方法で実装しています。

「Finance and Accounting」ロールが必要です。

### 売上差異の診断（`diagnose.py` → 画面表示のみ）

ダッシュボードに出る2つの売上が食い違うとき、原因を実データから切り分けます。
推測ではなく、シートの中身を数えて内訳を出します。

```bash
python3 diagnose.py --days 31
```

- 注文はあるのにASIN別売上が無い日を列挙
- 注文の状態別内訳（Shipped / Pending / Cancelled）と、価格が空欄の件数
- 配送料・ギフト包装料・消費税など、注文レポート基準の集計に含めていない金額
- 販路別・配送方法別の内訳

**Amazonは未発送（Pending）注文の価格を出しません。** そのため注文レポート基準の
売上は月末ほど小さく出ます。これは仕様であり異常ではありません。

### 月別シート・月次推移（`monthly.py`）

月次の振り返り用に、**月ごとに1シート**と、**月をまたいだ推移シート**を作ります。
Amazon APIは呼ばず、蓄積したrawシートを読むだけです。

```bash
python3 monthly.py               # 直近3ヶ月
python3 monthly.py --months 6    # 直近6ヶ月
```

#### 月別シート（例「2026-08」）の構成

**① 月間サマリー（前月比つき、原価・広告費を含む）**

| 指標 | 今月 | 前月 | 増減 | 増減率% |
|---|---|---|---|---|
| 売上 | ¥150,000 | ¥100,000 | ▲ +50,000 | 50.00% |
| 販売個数 | 60 | 50 | ▲ +10 | 20.00% |
| 1日あたり販売個数 | 30.0 | 50.0 | ▼ -20.0 | -40.00% |
| 平均単価 | ¥2,500 | ¥2,000 | ▲ +500 | 25.00% |
| セッション | 2,000 | 1,000 | ▲ +1,000 | 100.0 |
| 転換率% | 3.0 | 5.0 | ▼ -2.0 | -40.0 |
| 実入金額 | 127,500 | 85,000 | ▲ +42,500 | 50.0 |
| 実入金率% | 85.0 | 85.0 | → 0 | 0.0 |
| 原価合計 | ¥84,000 | ¥56,000 | ▲ +28,000 | 50.0 |
| 原価比率% | 56.0 | 56.0 | → 0 | 0.0 |
| 広告費合計 | ¥15,000 | ¥12,000 | ▲ +3,000 | 25.0 |
| 広告費比率% | 10.0 | 12.0 | ▼ -2.0 | -16.7 |

原価は商品名から自動判定します（下記「商品原価について」を参照）。
広告費はAmazon Adsの自動送信メールを取り込んだ `raw_ads_email` から算出し、
**税込（レポート記載額×1.1）** に換算して表示しています
（レポート上の金額は税抜きですが、実際の請求額は税込のため）。

**② 広告サマリー**

月間サマリーの直後に、広告関連の指標だけをまとめて表示します。

| 指標 | 今月 | 前月 | 増減 | 増減率% |
|---|---|---|---|---|
| 広告費合計 | ¥15,000 | ¥12,000 | ▲ +3,000 | 25.0 |
| 広告経由売上 | ¥45,000 | ¥40,000 | ▲ +5,000 | 12.5 |
| ROAS | 3.0 | 3.33 | ▼ -0.33 | -10.0 |
| ACOS% | 33.3 | 30.0 | ▲ +3.3 | 11.0 |
| 販売個数（広告経由） | 18 | 16 | ▲ +2 | 12.5 |
| 平均単価（広告経由） | ¥2,500 | ¥2,500 | → 0 | 0.0 |
| CPA（広告費÷販売個数） | ¥833 | ¥750 | ▲ +83 | 11.1 |
| セッション（広告） | 500 | 480 | ▲ +20 | 4.2 |
| 転換率%（広告） | 3.6 | 3.3 | ▲ +0.3 | 9.1 |
| 広告費の対全体売上比% | 10.0 | 12.0 | ▼ -2.0 | -16.7 |

当月が進行中の場合は「着地予想 広告費」「着地予想 販売個数（広告経由）」も表示します
（データのある日数の平均 × その月の日数）。

**③ 手数料の内訳**

販売手数料（紹介料）／FBA手数料（配送・保管）／その他手数料／プロモーション値引を
それぞれ前月比つきで表示し、最後に合計と**対売上比%**を出します。

**④ 売上変動の要因（前月＝100の指数）**

```
売上指数                150.0
　うち セッション指数    200.0
　うち 転換率指数         60.0
　うち 平均単価指数      125.0
検算（3指数の積）        150.0
主因   セッションの変動（広告・検索順位・在庫切れを確認）
```

増減率（±%）ではなく**指数（今月÷前月×100）**を使っています。
売上には次の恒等式が成り立つためです。

```
売上 ＝ セッション × 転換率 × 平均単価
```

指数なら要因が**正確に掛け算で分解できます**（200 × 60 × 125 ÷ 10000 = 150）。
増減率だと +100% と -40% が +50% にならず、足し引きが合いません。
検算行で分解が一致することを毎回確認しており、ずれた場合は警告を出します。

主因の判定は、3つの指数のうち**100から最も離れているもの**で行います。
セッションなら広告・検索順位・在庫切れ、転換率なら価格・レビュー・画像・カート獲得、
平均単価なら値引き・商品構成と、**確認すべき箇所が変わる**ためです。

**⑤ データの充足状況**

ASIN別売上・手数料/入金・広告データそれぞれの取得日数を、その月の日数に対して表示します。

**⑥ 日別の推移（広告・原価・利益額つき）**

日付 × 売上・広告費・販売個数・広告での販売個数・セッション・広告セッション・転換率・
広告転換率・手数料・実入金額・原価金額・**利益額**。末尾に合計行。
利益額 ＝ 実入金額 − 広告費 − 原価（広告費は税込）です。そのままグラフ化できる形にしています。

**⑦ 商品別ランキング（原価・粗利率つき）**

順位・ASIN・商品名・売上・**前月比%**・個数・セッション・転換率・手数料・
実入金額・原価合計・実入金率%・原価率%・**Amazon粗利率%**・返品数。

Amazon粗利率% ＝（実入金額－原価合計）÷ 売上。広告費は商品別に按分していないため、
ここには含まれません（広告費は月間サマリー・広告サマリー・日別の推移でのみ扱います）。

#### 商品原価について

商品原価は**商品名に含まれるキーワード**から自動判定します（ASINのハードコードは不要）。

| 原価（税抜・1個あたり） | 該当キーワード |
|---|---|
| ¥1,400 | エッセンス／美容液 |
| ¥1,300 | クリアローション／化粧水／ローション |
| ¥1,500 | ナイトクリーム |

いずれにも一致しない商品は原価0円として扱われ、`monthly.py` 実行時のログに警告が出ます。
新商品を追加した場合は `aggregate.py` の `PRODUCT_COST_BY_KEYWORDS` に追記してください。

#### Amazon Adsの実績取り込みについて（`ads_email_report.py` → シート `raw_ads_email`）

広告APIのアクセス許可（LWAスコープ）がAmazon側でまだ有効化されていないため、
つなぎとして、Amazon Adsが毎朝自動送信してくるレポートメール
（`no-reply@ads.amazon.com`、Gmail宛）をIMAPで読み取って代用しています。

このメールにはCSVが添付されておらず、本文中の「レポートをダウンロード」リンク
（Amazonのクリック計測リンク越しに期限付きの署名付きS3 URLを指す）をたどって
CSVを取得します。ログイン等の追加認証は不要です。

```bash
python3 ads_email_report.py                  # 直近3日以内のメールから最新の1通
python3 ads_email_report.py --search-days 7  # 検索範囲を広げる（復旧用）
python3 ads_email_report.py --dry-run        # 取得のみ。書き込まない
```

事前準備として、GitHubリポジトリの Settings > Secrets and variables > Actions に
`GMAIL_ADDRESS` と `GMAIL_APP_PASSWORD`（2段階認証＋
[Googleアプリパスワード](https://myaccount.google.com/apppasswords)）を登録してください。

広告APIのアクセスが有効化された段階で、専用スクリプトへの切り替えを想定しています。

#### キャンペーン別の内訳（月別シートの広告サマリーの右／`日別広告実績`シート）

月別シートの「■ 広告サマリー」の右側（H列以降）に、その月のキャンペーンごとの
内訳表を添えています。項目はインプレッション・費用・CPM・クリック数・CPC・CTR・
CV（購入数）・CVR・CPA・ROAS・ACOSです（費用は税込）。

日付ごとの内訳は月別シートには載せず、別シート「日別広告実績」
（`ads_daily_sheet.py` が作成、毎回全期間を作り直します）にまとめています。
列構成は月間の内訳表と同じで、日付とキャンペーン名の組み合わせごとに1行です。

```bash
python3 ads_daily_sheet.py               # 全期間を書き込む
python3 ads_daily_sheet.py --days 90     # 直近90日分だけに絞る
python3 ads_daily_sheet.py --dry-run     # 書き込まずに内容を表示
```

#### 過去データの一括取り込み（`backfill_ads_csv.py`）

`ads_email_report.py` が動き出す前の期間は広告データが無いため、Amazon広告
管理画面から手動でエクスポートしたCSVで埋められます。エクスポート元によって
列の並び順が違うことがあるため、位置ではなく列名で対応付けます。

```bash
python3 backfill_ads_csv.py エクスポートしたファイル.csv
python3 backfill_ads_csv.py エクスポートしたファイル.csv --dry-run
```

指定したCSVの期間分（最も古い日付以降）を、`raw_ads_email` の該当期間ごと
置き換えます。1回限りの復旧用スクリプトなので、自動実行（`run_all.py`）には
含まれていません。

#### 見た目

金額は **通貨表示（小数点なし、マイナスは赤）**、割合は `0.00%`、件数は桁区切りで
表示します。見出しは濃紺、表は1行おきに薄い背景、合計行は色を変えて強調します。
書式は `sheet_format.py` にまとまっており、色を変えたい場合は冒頭の定数を
書き換えるだけです。

#### 月次推移シート

| 月 | 売上 | 前月比% | 販売個数 | セッション | 転換率% | 手数料 | 実入金額 | 実入金率% | 返品数 | 取扱ASIN数 | データ充足 |
|---|---|---|---|---|---|---|---|---|---|---|---|

**「データ充足」列に ⚠ が付く月は、集計値が実際より少なく出ています。**
その月の `sales_traffic.py` を取得すれば埋まります。

### （旧）集計ダッシュボード（`dashboard.py` → シート `dashboard`）

蓄積したrawデータを結合し、商品別の実利益とKPIを1枚にまとめます。
Amazon APIは呼ばず、シートの中だけで完結します。

```bash
python3 dashboard.py             # 直近30日
python3 dashboard.py --days 90   # 直近90日
```

3つのシートを次のように突き合わせています。

| シート | 役割 |
|---|---|
| `raw_orders` | SKU ↔ ASIN ↔ 商品名 の対応表 |
| `raw_sales_traffic` | ASIN別の売上・セッション（Amazon公式の数値） |
| `raw_finances` | SKU別の手数料と実入金額 → SKUからASINへ集約 |

出力される商品別テーブル：

| ASIN | 商品名 | 売上 | 販売個数 | セッション | 転換率% | 手数料合計 | 実入金額 | 実入金率% | 返品数 |
|---|---|---|---|---|---|---|---|---|---|

**「売れているのに手元に残らない商品」が実入金率の低さで一目でわかります。**
保管手数料など特定商品に紐づかない費用は、サマリー欄に別枠で表示します。

#### 実入金額 ≠ 売上 − 手数料 である理由

シートには「売上から実入金までの内訳」も出力されます。

```
売上（Amazon公式・注文ベース）      800,000
  出荷タイミングのズレ              -3,000
商品代金（入金ベース）              797,000
＋ 税・配送料・その他売上            45,000
− プロモーション値引                -12,000
− 販売手数料                        -80,000
− FBA手数料                         -58,000
− その他手数料                       -5,000
＝ 実入金額（純額）                 687,000
```

単純な引き算にならないのは3つの理由からです。

1. **税と配送料が加算される**（売上には含まれない）
2. **プロモーション値引が引かれる**（手数料合計には含まれない）
3. **基準日が違う** — 売上は「注文日」、入金は「出荷日」。月末に注文されて
   未出荷のものは売上に載るが入金には出てこない

## 蓄積方式について

各スクリプトは**既存データを保持したまま、取得した期間だけを差し替えます**。
何度実行しても結果は同じで、重複も発生しません。

| シート | 差し替えの単位 |
|---|---|
| `raw_orders` | 取得期間（それより前の行は保持） |
| `raw_sales_traffic` | 日付ごと |
| `raw_finances` | 取得期間 |
| `raw_settlement` | 精算IDごと |
| `raw_ads_email` | 取得期間（メール本文の日付ごと） |
| `dashboard` | 毎回作り直し（派生データのため） |

**`sales_traffic.py` は取得済みの日をスキップします。** Data Kioskは1日1クエリ
（1〜3分）かかるため、これで日次実行が数分に収まります。ただし直近3日は
Amazonの数値が確定していないため、毎回取り直します。

全部取り直したい場合：

```bash
python3 sales_traffic.py --days 30 --refetch   # 取得済みの日も再取得
python3 main.py --replace                       # シートを全置換（過去データは消えます）
```

`--replace` は過去の蓄積を捨てるので、通常は使わないでください。

## 自動実行（毎日決まった時刻に動かす）

**現在の本番はGitHub Actionsです**（`.github/workflows/daily.yml`）。
このリポジトリにpushするだけで反映され、Macの電源やスリープ状態に左右されません。
以下の `install_launchd.sh` はローカルのMacで動かしたい場合の代替手段です
（GitHub Actionsと併用すると二重に実行されるので、どちらか一方にしてください）。

### GitHub Actionsでの自動実行

`.github/workflows/daily.yml` が、1日2回スケジュール実行されます。

| 時刻（JST） | cron（UTC） | 実行内容 |
|---|---|---|
| 毎朝7:00 | `0 22 * * *` | `run_all.py`（下表①〜⑤の本体一式） |
| 毎朝9:20 | `20 0 * * *` | `run_all.py --ads-only`（広告データの取込＋月次シート再生成のみ） |

広告メール（`no-reply@ads.amazon.com`）は毎朝8:45〜9:00頃に届くため、7:00の本体実行では
前日分のメールしか拾えません。9:20の追い上げ実行で当日分の広告データを取り込みます。

事前に、GitHubリポジトリの **Settings > Secrets and variables > Actions** で
以下のSecretsを登録してください。

| Secret名 | 内容 |
|---|---|
| `GOOGLE_SERVICE_ACCOUNT_JSON` | Googleサービスアカウントの鍵（JSON全体） |
| `LWA_CLIENT_ID` / `LWA_CLIENT_SECRET` / `LWA_REFRESH_TOKEN` | Amazon SP-APIの認証情報 |
| `SPREADSHEET_ID` | 書き込み先スプレッドシートのID |
| `GMAIL_ADDRESS` / `GMAIL_APP_PASSWORD` | 広告メール取り込み用のGmailアカウントとアプリパスワード |

実行状況は GitHub の **Actions** タブから確認できます。また `_log` シートにも
ジョブごとの成功/失敗が1行ずつ記録されます。今すぐ実行したい場合は、Actionsタブの
「Amazon日次レポート」→「Run workflow」から手動実行できます
（`full` にチェックを入れると長期間の取り込みになります）。

### ローカル（Mac）での自動実行（代替手段）

```bash
cd ~/exoplus_claude_code/amazon-report
chmod +x *.sh
./install_launchd.sh          # 毎朝6時
./install_launchd.sh 9 30     # 毎朝9時30分にしたい場合
```

登録前に、まず手動で通ることを確認してください。

```bash
./run_daily.sh
```

### 何が動くか

`run_all.py` が以下を順番に実行します。1つが失敗しても残りは実行されます。

| 順番 | ジョブ | 通常時 | `--full` 時 |
|---|---|---|---|
| 1 | 注文レポート | 直近30日 | 直近90日 |
| 2 | ASIN別売上 | 直近3日 | 直近30日 |
| 3 | 手数料・入金内訳 | 直近30日 | 直近180日 |
| 4 | 精算レポート | 直近3件 | 直近6件 |
| 5 | 広告データ（メール取込） | 直近3日 | 直近7日 |
| 6 | 月別シート・月次推移 | 直近3ヶ月 | 直近6ヶ月 |

`run_all.py --ads-only` を付けると、5と6だけを実行します（広告メール到着後の追い上げ用）。

ASIN別売上を「直近3日」にしているのは、**Amazonの数値が数日かけて確定する**ためです。
毎日3日分を取り直して上書きすることで、確定後の正しい値に自動で置き換わります。

数日ぶん実行が途切れた場合は、`./run_daily.sh --full` で取り返せます。

### 実行されたか確認する

**スプレッドシートの `_log` シート**に、実行のたびに1行記録されます。
ターミナルを見ていなくても、いつ動いて何件取れたかが分かります。

| 実行日時 | ジョブ | 結果 | 所要秒 | 詳細 |
|---|---|---|---|---|
| 2026-09-01 06:00:32 | 注文レポート | 成功 | 32 | 完了しました。48 件を書き込みました。 |
| 2026-09-01 06:04:11 | ASIN別売上 | 成功 | 219 | 合計 36 件を取得しました。 |

ローカルのログは `logs/` に日付ごとに残ります（30日で自動削除）。

```bash
tail -f logs/$(date +%Y-%m-%d).log     # 実行中の様子を見る
launchctl list | grep amazon-report    # 登録されているか確認
```

### スリープ時の挙動

**Macがスリープ中は実行されません。復帰したときに1回だけ実行されます。**
複数日ぶん跨いだ場合もまとめて1回です（何回も走ることはありません）。

各スクリプトは直近N日分を取り直す設計なので、**実行が遅れても数日飛んでも、
最終的にシートに入る内容は同じ**です。実害はありません。

定刻に動かしたい場合は、Mac自体を自動起動させる設定を追加できます
（電源アダプタ接続が必要）。

```bash
sudo pmset repeat wakeorpoweron MTWRFSU 05:55:00
```

### 解除

```bash
./uninstall_launchd.sh
```

## つまずいたときは

| 症状 | 原因と対処 |
|---|---|
| `環境変数が設定されていません` | `source .env` を実行していない。ターミナルを開き直した場合は毎回必要です |
| 認証で `invalid_grant` | リフレッシュトークンの値が違うか、コピー時に改行が混入している。前後の空白を確認してください |
| `スプレッドシートを開けませんでした` | **B-4の共有設定**を忘れている。サービスアカウントのメールアドレスに編集者権限を付与してください |
| `Google Drive API has not been used` | **B-2**でDrive APIを有効化していない |
| レポートが `CANCELLED` | 対象期間に注文が1件も無い。`--days` を増やして試してください |
| レポートが `FATAL` | ロール（権限）が不足している。工程A-1のロール設定を確認してください |
| `sales_traffic.py` が FATAL | **Brand Analytics** ロールが未付与。ポータルでロールを追加してください |
| `sales_traffic.py` が0件ばかり | 前日ぶんはまだ集計中の場合があります。`--days 7` で数日前まで含めて確認を |
| `is more than 90 days old` | 精算レポートは90日より前を取得できません。現在は自動で89日に制限しています |
| `settlement.py` が0件 | **Finance and Accounting** ロールが未付与か、直近89日に精算が無い |
| 文字化けする | 通常は自動判定されます。それでも化ける場合はご連絡ください |
| `レート制限` が何度も出る | 正常な動作です。自動でリトライするので待ってください |
